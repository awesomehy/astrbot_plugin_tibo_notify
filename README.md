# Tibo 动态订阅 · AstrBot 插件

将 [Tibo 网站](https://tibo-monitor.hhyan.me) 已完成中文翻译和分析的动态发送到已订阅的群聊或私聊。插件只读取网站结果，不抓取上游、不调用 LLM，也不改变现有 Server酱 通知。

## 指令

- `/tibo-notify on`：当前聊天从现在起订阅新完成处理的动态
- `/tibo-notify off`：当前聊天取消订阅，并取消尚未发送的消息
- `/tibo-notify status`：查看当前聊天订阅、待发数量和异常状态
- `/tibo 1`：查询最新第 1 条已完成动态
- `/tibo 3`：查询最新第 3 条，**只返回一条，不是最近三条**

`/tibo` 默认查询第 1 条。查询排序按网站原动态发布时间倒序；新动态推送按首次完成处理的顺序，因此较早发布但较晚完成 AI 处理的动态也不会遗漏。群聊中的不同成员不会生成重复群订阅。

## 安装与配置

目标版本：AstrBot **4.23.0 或更新版本**。已核对 4.23.0 官方 API，并运行离线单元/集成测试；未在真实 NAS、微信桥接器或微信聊天中验证送达。

1. 在 AstrBot 管理面板的插件安装页，通过仓库 URL 安装：
   `https://github.com/awesomehy/astrbot_plugin_tibo_notify`
2. 由机器人维护者登录 Tibo 网站，在账号面板中生成“个人只读订阅链接”。群成员不需要各自注册网站账号。**AstrBot 4.23.0 的配置界面不会遮挡这个链接**；建议在 NAS/容器管理器中设置环境变量 `TIBO_ASTRBOT_FEED_URL` 为完整链接，然后重启 AstrBot，插件链接设置留空。也可直接填入插件设置，但要注意下面的明文显示警告。
3. 在插件设置选择轮询间隔，默认 **300 秒**，运行时最低 **30 秒**、最高 86400 秒。修改配置并保存后生效，不需要修改代码；如当前管理面板要求重载，点击插件的重载按钮即可。
4. 将需要管理群订阅的人配置为 AstrBot 管理员，或填入插件“群订阅操作员白名单”，每项格式为 `平台实例ID:用户ID`。
5. 确保 AstrBot 的唤醒前缀包含 `/`。管理员先在自己的测试会话执行 `/tibo 1`，核对中文内容；再在需要接收通知的群聊执行 `/tibo-notify on`。
6. 等待网站出现下一条新完成处理的动态，确认**主动通知**确实到达。`on` 不会补发历史，也不会立即发送测试动态；查询回复正常不能证明主动推送正常。

### 凭据安全

完整个人链接是只读凭据，格式以 `#token=…` 结尾。不要发到聊天、公开 issue、日志或截图中。插件会在本地剥离 fragment，只通过 HTTPS Authorization 请求头发送凭据；不接受查询字符串 token、不跟随重定向、不会将凭据写进本地 SQLite。

Schema 已标记 `secret: true`，供支持该标记的新版 AstrBot 遮挡输入；但已核对 **4.23.0 的配置渲染器不支持此标记，链接会明文显示**。配置文件本身也不加密。不要在打开插件设置时直播、共享屏幕或截图。

优先使用固定环境变量 `TIBO_ASTRBOT_FEED_URL`，可使个人链接不出现在插件 WebUI/配置 JSON 中；它优先于界面输入。环境变量仍可能被 NAS/容器管理员读取，不是加密保险箱。修改容器环境变量后需要重启 AstrBot；若使用界面配置，应限制 `data/config/` 及备份的访问权限。丢失或泄露链接时，在网站轮换凭据，再更新环境变量或插件设置。插件只接受网站固定官方地址，避免把凭据误发到其他主机。

## 权限

- 群聊 `on/off` 默认仅允许 **AstrBot 管理员**或显式操作员白名单。
- 微信/QQ 的“群管理员”身份不自动等同于 AstrBot 管理员。
- 私聊默认允许用户管理自己的聊天，可关闭“允许私聊用户管理自己的订阅”。
- 查询默认向已订阅聊天开放，群成员可直接 `/tibo N`。管理员/操作员始终可查询。
- “额外查询用户白名单”只授予查询权限，不授予群订阅管理权限。
- `query_access=operators` 可收紧查询；`everyone` 会向机器人能够接收消息的所有聊天开放，请按实际使用范围选择。
- 白名单中的平台实例 ID 必须和 AstrBot 机器人配置对应，不是 `aiocqhttp` 这样的适配器类型名称。同一用户在另一平台实例不会自动得到白名单权限。

## 微信 OneBot v11 兼容性边界

插件使用 AstrBot 标准 `context.send_message(实际 UMO, MessageChain)` 主动发送，不调用特定微信桥接器的私有接口。订阅去重键包含平台实例、机器人自身 ID、群 ID/私聊用户 ID；发送路线保留真实事件的 UMO，不把群成员会话当成独立群订阅。

必须先做兼容性检查：

- AstrBot 4.23.0 官方 OneBot v11 主动发送代码会把目标会话转换为整数。如果桥接器直接暴露 `wxid_...`、`...@chatroom` 等非数字 ID，可能出现**被动回复正常、主动发送失败**。桥接器需要提供兼容的数字 ID 映射，或使用支持字符串 ID 的适配器/修复版本。
- 官方 OneBot 适配器会从群会话 UMO 末尾提取群 ID。不要自行改写 UMO；实际桥接器格式须与适配器匹配。
- 切换已有平台实例登录的机器人账号前，先在旧账号的订阅聊天执行 `off`；平台 ID 不变时，标准发送接口无法核实当前登录账号仍与旧订阅一致。
- 同一平台实例不要混接多个机器人身份。插件的存储按机器人隔离，但标准 UMO 发送接口按平台实例路由，不能保证共享实例内的多机器人定向。
- `context.send_message` 返回 `True` 只表示找到平台并完成适配器调用，**不是微信送达回执**。插件不会声称恰好一次送达或真实微信已验证。

如果出现失败，先检查 `/tibo-notify status`、AstrBot 机器人连接状态、桥接器版本和 ID 映射。反馈问题时只提供版本、脱敏错误类型和会话格式，不能提供个人订阅链接、Authorization 头或完整聊天内容。

## 可靠性和重启行为

- 每个插件实例只维护一个增量接收器。多个订阅群共用拉取结果，不按群重复轮询。首次开启某个聊天会额外读取一次最新服务器基线；重复 `on` 不修改现有起点。
- 第一次安装先建立基线，不把网站历史内容群发。重启/重载会保留原接收游标，继续补收停机期间的新动态。
- 每页数据、本地缓存、每个聊天的待发记录和接收游标在同一个 SQLite 事务中提交。提交成功后才开始发送；保存失败不会提前推进游标。
- 每个聊天单独记录发送状态。明确“没有找到平台”的返回值可安全重试；发送异常、超时或进程在发送途中退出属于结果不确定，不盲目重发，并暂停该聊天后续发送。
- 不确定发送需要先核对聊天记录。确认后 `off` 再 `on` 可从当前服务器起点恢复，旧消息不会自动重发。需要的旧内容可用 `/tibo N` 手动查询。
- `off` 取消还没开始的发送，已提交平台的消息可能仍会到达。关闭后重新开启使用新基线，旧的在途失败不会被重新排队。
- 令牌轮换但 feed 身份相同会保留订阅与游标；换成另一个账号/订阅源会关闭原订阅，需在各聊天重新开启，避免跨账号沿用订阅。
- 普通网络故障、503、429 会退避并保留数据，已持久化待发消息可继续分发。429 的 `Retry-After` 支持等待至次日北京时间零点，最长 86400 秒，不会被本地较短退避截断；等待期间不会继续轮询或通过查询/开启订阅重复访问。401/403 凭据失效会暂停发送，直到更新配置。
- 网站显式重处理较早动态时，若它暂未完成，增量游标会停在该条之前，并至少等待服务端要求的重试间隔。后续处理修复后继续；不会为了“看起来最新”而跳过失败条目。
- 管理面板禁用、重载或退出时会取消并等待接收任务退出、关闭 HTTP 会话和数据库；重复初始化不会创建第二个后台任务。

持久化文件位于 AstrBot 的 `data/plugin_data/astrbot_plugin_tibo_notify/state.sqlite3`。NAS/Docker 应持久化整个 AstrBot `data` 目录。迁移时先停用插件，再备份数据目录。不要通过删除数据库来“修复游标”，否则会失去原订阅和去重状态。不要同时运行两个实例并共用同一个 SQLite 文件。

## 限制与费用

默认 300 秒一次，空闲时约 **288 次请求/天/实例**。首次启动、首次开启会话、手动查询、补收分页会额外请求。实际免费额度由网站服务商和该账号其他流量共同决定。

- 单页请求最多 10 条，单轮最多 5 页；更大积压在后续轮次继续补收
- 分发独立于轮询间隔，每批最多 20 次发送，发送间隔 0.5 秒；失败聊天不阻塞其他聊天
- 查询默认每聊天 5 秒冷却，全实例还限制每秒最多一次；最大序号 100，可在配置中降低
- 默认最多 200 个订阅聊天，可设置为 1–2000
- 手动查询依次显示 `最新第 X 条`、`【Codex重置预告：是/否】`、原文、中文翻译；自动推送以 `【Codex重置预告：是/否】` 开头，不显示查询序号，同样先原文后译文
- 底部仅保留 UTC 发布时间、北京时间（UTC+8）及原文链接；查询和自动推送均不显示 AI 判断说明或翻译模型
- 判定采用网站已保存结果，插件不额外生成分析理由或调用模型
- 单条消息最多 3500 字符。超长原文与译文平分剩余预算，短字段未用完的空间让给另一字段；被截断的字段明确标注“内容已截断，完整内容见链接”，顶部判定及底部时间、链接完整保留
- 本地保留近期缓存及未解决的投递记录；长期离线/发送不确定的聊天可能积累待发状态，应定期检查

## 更新

- **v1.0.1**：手动查询序号移到首行；判定标题改为 `【Codex重置预告：是/否】`；正文先原文后中文翻译，移除消息底部的 AI 判断说明和翻译模型行。保留原有订阅与 SQLite 状态，不需要重新订阅。

## 本地测试

无需真实网站凭据、AstrBot 安装或聊天平台即可运行离线测试：

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
python -m compileall -q .
```

覆盖：首次基线、fresh-on、同群不同成员去重、不同平台/机器人隔离、页缓存/游标原子回滚、重启恢复、发送中断隔离、off/on 竞态、限流退避、查询序号/权限/冷却、配置间隔变化、任务取消、fragment 凭据、拒绝重定向、响应体限额与协议校验。

CI 使用 Python 3.10–3.13 运行相同测试。离线测试通过不等于真实微信平台验证通过。
